# Feature Benchmarking（竞品/功能对标调研）

目标：服务 UX / UI 设计前期的 benchmark 与参考样本收集，用真实可追溯的来源帮助设计师理解同类产品如何组织页面、呈现信息、设计控件、安排操作路径和反馈状态，并沉淀可迁移的交互与视觉参考。

核心原则：HTML 优先阅读与归档、截图可见、结论可回链、先做 Source Pack，再由用户确认是否进入 Canvas Benchmark。

## 文件职责

- `SKILL.md`：阶段流程、输入、产物和用户交互。
- `rules.md`：调研范围、候选、来源、截图、证据和 Insight 的内容标准。
- `output-spec.md`：Source Pack、Canvas、Checklist 与单产品附录的页面结构。
- `delivery-checklist.md`：交付前的最终核验；不重复定义规则。

执行前必须读取 `rules.md` 与 `output-spec.md`，交付前必须按 `delivery-checklist.md` 核验。

默认调研目的：除非用户明确说明用于市场进入、产品定位或竞品监测，本技能默认以「借鉴怎么设计」为主要目的，重点寻找可迁移的页面结构、交互路径、控件模式、信息呈现和视觉处理方式。

用户需求优先：以用户当次对话里的 UX / UI 需求确定检索方向和样本组织方式。用户明确提出的产品、页面、交互、布局、视觉素材或场景优先级最高。

承接需求整理：如果当前任务已有 `design-req-organizer` 输出，本技能必须优先承接其中的推荐调研点。范围确认应把这些调研点作为默认假设简要复述，让用户确认、纠正、重排优先级，或从中选择一个/几个重点调研。若用户未选择，Source Pack 默认覆盖全部推荐调研点；若用户纠正，则以用户纠正后的调研点为准。

主题边界：调研主题来自用户 prompt、`design-req-organizer` 产物或用户明确补充的新范围。竞品样本、截图质量、检索中新发现的产品都不能反向改变调研主题或调研框架；新增样本只能服务已确认调研点。

产品形态包括但不限于：B 端控制台、SaaS 工作台、开发者工具、IDE / IDE 插件、数据平台、企业协作工具、AI 产品、AI 应用产品、AI Copilot / Assistant、AI Agent 编排 / 自动化平台、桌面端、浏览器插件等。移动端默认不纳入，除非用户明确指定，或本次 UX / UI 问题本身是移动端场景。

Source Pack 默认主动扩展候选：用户给出的产品、厂商或链接是 P0 seed，必须覆盖；用户已有样本也应进入 Source Pack 做证据核验和粗略分析。按本次产品形态选择相关厂商生态检索产品与文档，例如 B 端 / 云产品可参考字节 / 火山引擎、阿里云、AWS、Google Cloud、Azure、腾讯云、华为云等；具体候选按本次 UX / UI 主题和已确认调研点筛选。

候选筛选原则：优先选择能为当前设计问题提供可迁移参考的产品，而不是单纯名气最大或市场份额最高的产品。筛选时看：是否覆盖当前功能 / 页面 / 流程；是否能看到真实界面、操作截图、demo 或文档截图；是否代表一种不同设计思路，如更高信息密度、更强引导、更复杂权限或更成熟工作流；是否与目标用户、产品形态、业务复杂度相近；是否有近期迭代、用户反馈或行业讨论可作为补充证据。

来源与图片强约束：Source Pack 的对象是设计师，素材必须能帮助理解页面与交互。官方文档用于确认产品、功能和语境，点名主竞品必须检索；展示图片不要求来自官方文档。图片可以来自官方文档、产品页、教程、视频、测评、产品分享文档或图片搜索回链页面，但必须确认属于目标产品 / 功能，且能帮助设计师理解界面或交互。图片搜索可用于发现候选素材；最终是否纳入，以来源页是否明确属于目标产品 / 功能、是否能帮助理解目标页面或交互为准。

非官方材料强约束：官方材料必须有，但不能只看官方材料。每个主样本尽量补 1–2 条有设计价值的非官方材料。检索入口包括 review、tutorial、walkthrough、demo、screenshot、product guide、pdf、video、developer article、product strategy、launch analysis、implementation guide、best practice、case study、webinar、conference talk、blog、newsletter、deck、slides 等。非官方材料是否合格，不看它是不是“评测”，而看它是否能帮助设计师理解目标产品的页面形态、入口、控件、操作路径、状态反馈或用户痛点。

## 1. 什么时候使用

- 做某个功能/页面/流程的竞品调研
- 需要真实产品界面、页面结构、交互路径、关键状态作为设计参考
- 用户问“有没有类似产品”“别人怎么做”“这个功能怎么设计”
- 为设计评审准备可回链证据和可迁移结论
- 需要让用户明确“参考哪些竞品的哪些部分”，再交给 `design-definition` 更新 AI 设计输入

## 2. 必要输入

最低 3 项：

1. 功能名（中/英）
2. 场景/入口：用户从哪里进入，要完成什么任务，成功标准是什么
3. 目标用户：角色、熟练度、行业、B/C 端

可选：

- 候选竞品名单
- 产品形态：B 端控制台 / SaaS 工作台 / 开发者工具 / IDE 插件 / 数据平台 / 企业协作工具 / AI 产品 / AI 应用产品 / AI Copilot / AI Agent 编排平台 / 桌面端 / 浏览器插件等
- 指定链接或截图

## 3. 工作流

### 范围确认｜Scope Confirmation

快速确认调研假设，3–6 行即可：

- 功能范围
- 入口/任务
- 用户角色
- 需要重点看的调研点；若已有 `design-req-organizer` 推荐调研点，直接承接并复述这些点

同名多义时，只追问 1 个澄清问题，然后继续执行。

### Source Pack｜粗略分析与样本池

默认交付：`00_source_pack.html`

作用：先让用户“看界面 + 看来源 + 看粗略判断 + 选调研点/样本”。首次调用本技能默认只交付 Source Pack，然后等待用户确认是否继续。从零开始的调研不支持跳过 Source Pack 直接进入 Canvas Benchmark；只有当前任务已有可承接的 Source Pack，用户确认继续后才进入 Canvas。

Source Pack 副标题用一句话说明本步提供什么、帮助用户做什么，并带出下一步。不要写泛泛的“粗略分析与样本池”。推荐写法：`{DATE} · 本步提供{对象/页面}样本与证据索引，用于选择产品并进入下一步 Canvas 深拆`。

HTML 必须包含：

- `output-spec.md` 规定的页面结构；`rules.md` 规定的候选、来源、截图与内容标准。
- 基于 `templates/source-pack.html` 修改内容，保持 CSS、卡片结构和 Sources 样式稳定；截图资产存入本次输出目录的 `assets/`。
- 交付前运行 `scripts/validate_source_pack.py {输出目录}/00_source_pack.html`；失败先修复，不交付失败版本。

Source Pack 交付后的回复必须只提示下一步 Canvas Benchmark，不提前提 Design Reference Checklist。回复结构必须清楚写出：已生成的 Source Pack 文件、不会自动进入 Canvas、用户需要选择 3–6 个产品、只回复“继续/按推荐继续”时会使用的默认产品、Canvas 会覆盖的调研点。推荐文案：

```text
已生成 Source Pack：00_source_pack.html

你可以先看候选产品、截图和来源。下一步不会自动进入 Canvas；如果要继续，请从候选产品里选 3–6 个想深拆的产品。

如果你只回复“继续”或“按推荐继续”，我会按开头“建议优先深拆”的产品进入下一步：
{默认产品列表}

Canvas Benchmark 会围绕这 {N} 个调研点展开：
- {调研点 1}
- {调研点 2}
- {调研点 3}
```

### Canvas Benchmark｜进一步分析画布

触发条件：当前任务已有可承接的 Source Pack，且用户看完后明确要求继续深入，或明确说“继续 / 按推荐做 Canvas / 做横向对比 / 深入画布 / 只看某几个调研点”。没有当前任务可承接的 Source Pack 时，先生成 Source Pack。

默认交付：

- `01_canvas_benchmark.html`：画布式横向对比，给人阅读和评审
- `02_design_reference_checklist.html`：可选的用户采纳页；只在用户要求筛选可用于后续设计的竞品参考时生成。
- `assets/`：报告引用的本地截图资源

Canvas 的形式固定为“调研点 × 产品”：

- 页面结构与证据、Insight、样本标准分别以 `output-spec.md` 与 `rules.md` 为准。
- 基于 `templates/canvas-benchmark.html` 修改内容，保持画布结构、矩阵样式、空格子留白和截图说明样式稳定。

Canvas Benchmark 完成后，只在用户明确要筛选竞品参考时生成 Checklist；不要自动生成 Checklist。

Canvas 样本规则：

- 产品默认来自 Source Pack 的推荐和用户确认，也允许加入用户新增指定样本
- Canvas 必须承接用户选定产品在 Source Pack 中的产品介绍、推荐理由和关键取舍；若用户新增产品，则在 Canvas 中补齐同等粒度的产品介绍和推荐理由
- 研究过程中必须先补充用户选定产品在当前调研点下的细证据；也可以补充强相关样本，但必须在报告里标注“Canvas 新增参考”，并说明加入原因和来源
- 新增样本只能补强当前调研点，不能替换用户点名样本，不能改变来自用户 prompt 或 `design-req-organizer` 的调研主题
- 不强制每个产品都有每个调研点的截图；缺证据留空

单产品页规则：

- 默认不生成 `products/{product}.html`
- 只有用户明确要求深拆某个产品、某个产品在 Canvas 中占比很高、或某条流程需要单独展开时，才生成单产品附录页
- 单产品页是可选附录，不是 Canvas Benchmark 的必交付物

### 与后续技能的衔接

Canvas Benchmark 不直接生成设计。Checklist 中的用户确认内容与 Canvas 作为后续设计的输入；未确认 Insight 只保留在竞品报告中。

## 4. 分析维度

按项目选择，不必全部展开。Canvas Insight 可按三层收束，但不要机械展开：

- 感知层：页面形态、视觉层级、信息密度、默认视图
- 行为层：任务路径、控件组织、交互效率、状态反馈、异常处理
- 价值层：目标角色、核心场景、设计意图、差异化价值、可迁移性

具体调研维度包括：

- 信息架构：入口、导航、层级深度、对象命名
- 默认视图：默认展示什么，隐藏什么，如何渐进展开
- 检索能力：搜索、筛选、排序、分组、保存视图
- 详情/Inspector：信息组织、解释性、可操作性
- 核心交互：选中、下钻、回退、批量、快捷操作
- 闭环动作：导出、分享、订阅、通知、协作
- 权限与不可见态：看不到、不能点、申请入口、审计提示
- 异常与边界：空态、失败、长耗时、冲突、规模过大
