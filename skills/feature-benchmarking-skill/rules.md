# Feature Benchmarking Rules

## 1. 基本原则

- HTML 是默认交付与归档形态。
- 不编造：所有结论必须可回链到来源 URL。
- 默认先产出 Source Pack；用户确认继续后再产出 Canvas Benchmark。
- Source Pack 是粗略分析与样本池，不是纯链接列表。
- Canvas Benchmark 是进一步分析画布，固定为“调研点 × 产品”的横向矩阵。
- 面向 UX / UI 设计师做页面与交互参考，优先选择能看出页面形态、信息结构、关键控件、交互路径、状态反馈和工作流的素材。

## 2. 主题与调研点

- 调研主题来自用户 prompt、已有需求整理产物，或用户明确补充的新范围。
- 如果已有 `design-req-organizer` 输出，必须优先承接其中的推荐调研点。
- 范围确认只复述和确认调研假设，不重新发明调研点。
- 用户可以确认全部推荐调研点，也可以从中选择一个或几个重点调研点。
- 如果用户指出调研点不准确或需要调整，以用户纠正后的调研点为准。
- 竞品样本、截图质量、检索中新发现的产品都不能反向改变调研主题或调研框架。
- 新增样本只能补强当前调研点；如果新样本只服务另一个主题，则不进入当前报告，可放入“后续可调研”。

## 3. Source Pack 规则

- 默认只产出 `00_source_pack.html`。
- 候选产品默认 10–15 个；数量不够不要硬凑，可以减少数量，但必须写清原因。
- 用户点名的产品、厂商或链接是 P0 seed，必须进入检索。
- 用户已有样本也进入 Source Pack，做证据核验和粗略分析，而不是自动跳过 Source Pack。
- Source Pack 应主动扩展候选样本，按本次产品形态选择相关厂商生态检索产品与文档，例如 B 端 / 云产品可参考字节 / 火山引擎、阿里云、AWS、Google Cloud、Azure、腾讯云、华为云等。
- 每个产品至少包含 1 个有效产品视觉来源。有效视觉来源指真实产品界面、控制台、侧边栏、输入区、工作流截图、官方演示图或可截图的视频/文档页面。
- 每个产品必须有 2–3 张预览图；最终 HTML 必须引用本地 `assets/` 文件，不得依赖外站热链。
- 每个产品写一句产品介绍、1 句推荐理由、1 句注意/取舍。
- 调研范围区必须简洁但信息完整：问题写要研究的设计问题，并明确属于交互、信息架构、视觉布局、内容组织或流程中的哪一类；目标写本步要帮助用户做出的选择或决策结果，并结合本次推荐调研点写成完整句；参考类型写样本来源范围；每项优先控制在 16–48 个中文字符，避免压缩成单个标签或关键词列表。
- Executive Summary / 关键结论必须简洁但可读：1 句总判断 + 3–5 条要点；每条只写 1 个肯定句设计判断，并说清对象/场景、设计动作和用户价值，避免压缩成口号。
- Sources 少而准；每个正式产品卡片必须有 3–5 条高质量链接，其中至少 1 条官方来源、至少 1 条非官方来源。若某产品来源数量不足或缺少官方/非官方任一类型，默认移入“证据待补”，不要作为正式候选卡片。
- 纯 API、SDK、参数表、技术原理、无界面说明页只能作为内部研究依据或补充来源，不能替代视觉来源，也不要放进可见 Sources 凑数。
- Source Pack 结尾必须给出明确的下一步入口，标题建议使用“下一步：生成 Canvas Benchmark”，并说明不会自动进入下一步；必须告诉用户下一步需要从上方候选产品里选择要深拆的产品，推荐 3–6 个产品；用户只回复“继续”或“按推荐继续”时，默认按推荐产品进入 Canvas Benchmark。下一步模块上方必须放「Canvas 深拆推荐」表，展示「功能点 → 下一步看什么 → 重点参考产品」，用于帮助用户决策下一步优先深拆哪些产品；该表支持 2–5 行，实际数量以 Source Pack 开头目标/范围里的调研点为准，不强制 5 个，也不能漏写或硬凑。下一步模块本身不再重复产品推荐表，只保留产品选择说明和可编辑、可复制的确认文本。确认文本里的默认产品选择必须沿用 Source Pack 开头「建议优先深拆」里的推荐产品；确认文本必须逐条列出调研点，并说明 Canvas 会用所选产品分析这些调研点，不能只写“全部调研点”。
- 不单独放“推荐调研点”区块；调研点应体现在调研范围的目标行和底部下一步卡片里。
- Source Pack 完成后等待用户确认；不要默认继续生成 Canvas。
- Source Pack 交付后的 final message 只提示可继续生成 Canvas Benchmark，必须写清不会自动进入 Canvas、默认继续时使用的产品列表，以及 Canvas 会覆盖的完整调研点列表。
- Source Pack 交付前必须运行 `scripts/validate_source_pack.py`，校验失败时先修正 HTML，不交付失败版本。
- 截图资产放在每次调研输出目录的 `assets/` 中；skill 目录自身不放通用截图资产。

## 4. Canvas Benchmark 规则

- 只有用户看完当前任务的 Source Pack 并确认继续后，才生成 Canvas。从零开始的调研不支持跳过 Source Pack 直接进入 Canvas；如果用户先要求横向矩阵 / 深入画布，但当前任务没有可承接的 Source Pack，仍先生成 Source Pack。
- Canvas 文件名统一为 `01_canvas_benchmark.html`。
- Canvas 必须使用“调研点 × 产品”的矩阵结构。
- 表头是产品，左侧是调研点。
- Canvas 表头每个产品名下必须继承 Source Pack 中该产品的产品介绍和推荐理由；若用户新增产品，需补齐同等粒度介绍和推荐理由。
- 每个交叉格只放该产品在该调研点下的证据：截图 + 简短总结。
- 没有对应截图或可核验证据的格子必须留空，不放替代图。
- 每个非空格子应包含：本地截图、图片标题、来源 URL、1–3 条总结。
- 截图来源直接写在格子内或图片说明下，不集中堆到文末。
- Canvas 必须在 Source Pack 基础上追加细查，不能只复用 Source Pack 的 3–5 条产品级 Sources。追加来源应服务具体格子，优先是该调研点对应的功能页、帮助文档、产品指南、教程、视频截图页、release/blog 或第三方 walkthrough；每个非空格子至少有 1 条直达来源 URL。整体来源数量通常应多于 Source Pack。
- Canvas Matrix 最后一行必须是「Reference Links」，按产品汇总本次 Canvas 使用过的所有来源链接，包括 Source Pack 继承来源和 Canvas 追加来源；格子内来源不能替代该行。
- 产品默认来自 Source Pack 推荐和用户确认。
- 用户可以新增产品；研究过程中也可以补充强相关样本。
- 新增样本必须标注“Canvas 新增参考”，说明加入原因和来源。
- 新增样本不能替换用户点名样本，不能改变调研主题。
- 不强制每个产品覆盖所有调研点；证据不足就留空。
- Canvas 完成后，只有用户明确要筛选可采纳的竞品参考时才生成 `02_design_reference_checklist.html`；不要自动生成 Checklist。

### Design Insights

- Insight 必须来自 Canvas 中已有证据，写成可执行设计判断，不得复述竞品做法或泛泛写价值。
- 每条必须包含明确的设计取舍、触发条件或边界规则；`看到` 点名产品与机制，`说明` 写适用条件或风险，`对你的启示` 落到本需求对象、默认规则、控件、布局或状态处理。
- Insight 应短句化；复杂解释拆成更小的 Insight 或收回来源格子的总结，避免在 Insight 表堆长段。

## 5. Optional Outputs

- 默认不生成 `products/{product}.html`。
- 单产品页只在用户明确要求、产品需要完整路径说明、或某个产品在 Canvas 中证据量很大时生成。
- `02_design_reference_checklist.html` 是可勾选的竞品参考取舍页，不是普通调研报告或评审材料。
- Checklist 每条必须包含来源产品、对应调研点、可参考点、适配提醒和“采纳此参考”选择；用户确认内容汇总为可复制的参考摘要，不展示内部证据位置。
- Checklist 数量不设硬限制；每条必须能被用户独立判断是否采纳。

## 6. 与 design-definition 的衔接

- Canvas 结束后，不直接进入设计生成。用户确认的 Checklist 内容作为后续设计技能的输入。
- 传递的竞品输入包括 Canvas、可选单产品附录和用户从 Design Reference Checklist 复制出的确认内容。
- 未经用户确认的竞品洞察只能留在报告中，不得写入设计输入。
- 参考选择清单只记录“竞品哪些部分可参考/不可参考/如何变形参考”；不得替代需求整理产物里的业务事实、对象关系和流程边界。

## 7. 来源优先级

1. 官方文档中心 / 帮助中心 / 控制台操作文档中含真实界面或流程截图的页面
2. 官方产品截图、官方产品页、官方教程、官方博客、官方视频
3. 可信第三方教程、测评、产品分享、开发者文章、策略分析、最佳实践、webinar、slides 中含真实界面或操作流程的页面
4. 图片搜索回链页，必须点回来源页核验产品归属、功能语境和页面价值
5. 用户提供截图或实机截图
6. App Store / 应用商店 / 截图聚合站，默认不用于 B 端控制台调研
7. 设计社区概念稿，仅可作为“非真实产品参考”，必须标注

## 8. 分析写法

Source Pack 产品卡片：

1. 产品定位
2. 为什么相关
3. 适合参考什么
4. 不适合照搬什么
5. 来源链接

Canvas cell：

1. 截图或局部特写
2. 图片标题
3. 来源 URL
4. 1–3 条短总结，写成可落地观察

## 9. 质量门槛

- HTML 能本地打开，关键图片可见。
- 关键结论都能回链。
- 图片内容必须和产品名、调研点、格子描述一致；不得用其他产品截图替代。
- 不重复放同一张图，除非同一截图确实支撑多个调研点。
- Canvas 没证据的格子留空。
- 建议落到具体设计决策：默认视图、控件选择、输入区策略、上下文边界、异常态或交互策略。
