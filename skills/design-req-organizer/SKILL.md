# 设计需求整理技能

将会议纪要、聊天记录、语音转写稿等原始材料，提取为面向设计执行的结构化需求整理结果，让设计师快速判断“要设计什么、不能怎么设计、哪些还没定”。

## 默认产出

本技能默认产出同一需求的需求整理页：

0. 文件命名规则
   - 开始输出前必须基于需求内容重新总结一个清晰需求名，再转成稳定 slug；不要只沿用文件名、会议标题或原文里的临时叫法。中文需求名可保留中文，英文用小写 kebab-case。
   - 文件名必须包含该需求名 slug：`design-requirement-brief-[需求名].html`。
   - 如果 workspace 中已存在同名需求产物，判断为同一需求时直接更新该组文件；如果不是同一需求，必须换用更准确 slug，不能覆盖其他需求产物。
   - 只有用户明确要求兼容历史流程，且确认不会覆盖其他需求时，才允许额外创建不带需求名的通用入口或副本。

1. `design-requirement-brief-[需求名].html`
   - 给人看的需求整理页。
   - 保留原有 `Human Requirement Brief` 的内容结构，并在背景后增加 `5W1H`；材料明确给出版本范围、复用边界或不做范围时，在第一步输出 `Current Scope / Boundary`。默认结构：背景、5W1H、Current Scope / Boundary（可选）、设计目标、用户与影响范围、设计重点关注、设计约束条件、设计相关结论、交付内容与时间节点、待确认问题、建议竞品调研关注点、可选下一步：feature benchmarking。
   - 目标是提升可读性，适合 PM / 设计师快速阅读，不作为设计评审页替代品。

`ai-design-input-[需求名].md` 不属于本技能默认产物。只有用户明确要求生成、更新或补全 AI Input 时，才调用 `ai-design-input` 生成；不得因完成需求整理而自动新建。若同一需求已存在 AI Input，本次整理确认了会影响页面范围、对象关系、流程、状态、权限或操作粒度的逻辑变化，则必须自动调用 `ai-design-input` 同步更新；仅更新已确认变化，不重建或扩写其他内容。

## 适用场景

- 用户上传或粘贴了会议记录、聊天记录、语音转写稿
- 用户希望提取其中的设计相关信息
- 材料可能口语化、混杂闲聊、含说话人标注和时间戳
- 用户同时提供了多份材料（draft PRD、会议纪要、聊天记录），希望综合整理出当前有效的设计信息

Brief 必须包含「建议竞品调研关注点」与可复制的 `feature benchmarking` 输入；内容规则以 `rules.md` 为准。

## 🔒 Step 0：多源材料预处理（有多份材料时，开始输出前必须先执行）

按顺序逐项判断，完成后再开始写输出：

1. **是否有会议记录？**
   - 有 → 以会议记录为主干，其他材料只能补充会议已提到的点，不能新增范围
   - 没有 → 以最具体、最晚的材料为主

2. **PRD 与会议是否冲突？**
   - 冲突 → 优先采用更晚、更具体、更像拍板的表述；无法判断则标注 ⚡ 并放入待确认
   - 不冲突 → 会议内容为主，PRD 作补充细节

3. **PRD 是否有会议未覆盖的新内容？**
   - 有 → 不写入输出，除非会议明确说"看 PRD""按 PRD 为准"
   - 会议明确指向 PRD → 可补入，并标注"会议补充参考 PRD"

4. **是否存在多条内容指向同一设计点？**
   - 是 → 先合并，再分类；不要把同一设计点拆成多条写进不同章节

---

## 🔒 Step 0.5：材料理解澄清闸门（开始输出前必须先执行）

遇到以下情况时，必须先向用户提问确认，不能直接生成 / 更新产物：

1. **指代不清**
   - 材料中出现“这个 / 那个 / 它 / 这里 / 后面 / 这块 / 那块”等指代，且无法从上下文唯一判断主语或对象。
   - 这类问题不是「待确认问题」，而是「材料理解前置澄清」；确认前不得写入最终产物。
   - 提问格式应直接列出可选解释，例如：`“这个要审批”里的“这个”是指 Service、Record 还是 Remark？`

2. **专有名词不稳**
   - 语音转写中出现疑似误识别的专有名词、字段名、对象名、页面名、状态名或技术口径，且会影响对象关系、流程、字段、权限或生效粒度。
   - 不得自行标准化成看似更合理的新词；应保留原词并提问确认，或在用户确认前不写入硬逻辑。

3. **多个来源口径不一致**
   - 人工纪要 / 截图 / 明确文字的优先级高于语音转写。
   - 如果人工材料与语音转写冲突，以人工材料为准；仍无法判断时先问用户。

---

## 🔒 Step 0.75：待确认问题闭环扫描（分类前必须执行）

对每个曾被提出的问题或未决项，按时间顺序检查：

1. 后续会议是否已经回答。
2. 更新材料是否已经拍板或明确排除。
3. 用户是否已经补充确认。

已有答案的内容必须移入对应的设计约束条件或设计相关结论，不得继续保留在待确认问题中。只有仍需 PM / 业务 / 研发给出外部答案、且答案会影响设计推进的问题，才允许进入待确认问题。

## 🔒 分类判断树（每条信息必须过一遍，再决定放哪里）

```
Q0: 这条信息只是协作闲聊、设计还原度、研发配合方式、工具吐槽、demo 制作过程、会议寒暄吗？
    → 是 → 不输出；只有明确负责人、截止时间、交付物、发布节点时，才放入「交付内容与时间节点」

Q1: 这条信息是"外部条件导致设计不得不遵守的规则"吗？
    → 是 → 设计约束条件

Q2: 有决策权的人是否已明确拍板 / 排除某个方向，且未被后续材料推翻？
    → 是 → 设计相关结论

Q3: 材料是否明确指出了具体对象或场景中的设计难点 / 矛盾，并说明它会影响理解、判断、操作、流程或状态？
    → 是 → 设计重点关注

Q4: 需要 PM / 研发给出答案，设计师无法自行决定吗？
    → 是 → 待确认问题

Q5: 只是建议、候选方案、个人倾向、参考方案或普通设计选择吗？
    → 是 → 不输出

以上都不是 → 根据内容进入设计目标或背景
```

**高风险边界提示：**
- "采用 A 样式还是 B 样式""放面板还是做摘要"如果只是列举候选方案 → 不输出；不能仅因存在多个方案就写成设计重点关注
- "哪些字段必须保留""是否合并流程"→ 待确认，不是设计重点关注
- 会议只是"有人倾向""感觉也可以""可以这样做"→ 未拍板，不能写进设计结论
- 只有材料明确提出具体设计难点 / 矛盾及其影响时，才进入设计重点关注；不能由整理者根据候选方案自行推断难点
- 有上位结论但细节未定 → 上位结论进设计结论，细节作为设计目标覆盖
- "研发尽量按稿实现""设计还原度验证""前端可能实现不一致"→ 不写进约束、结论或重点关注
- "研发 effort 大""可能做不到"只有在研发明确确认无法实现时，才可写入约束；需要研发确认时放待确认，否则不输出

---

## 🔒 输出质量闸门（最终回答前必须执行，不要展示过程）

在输出最终结果前，必须对已生成内容做一次不可见自检。只要命中任一失败项，必须先重写对应章节，再给用户最终答案：

1. **约束条件失败项**
   - 出现协作闲聊、还原度验证、研发配合方式、工具吐槽、demo 制作过程
   - 出现没有限制设计方案的项目管理信息
   - 出现未被明确确认的研发实现猜测

2. **设计结论失败项**
   - 出现"可以试试""感觉""我觉得""想看看""能不能"这类未拍板倾向
   - 出现候选方案、个人建议、参考方案或未被明确确认的承载方式、样式方向、显隐策略
   - 结论没有明确决策语义、决策权来源，或已被后续材料推翻

3. **设计重点关注失败项**
   - 只列了候选方案或普通设计选择，没有材料明确提出的设计难点 / 矛盾及其影响
   - 把需要外部回答的产品口径包装成设计难点
   - 根据常识自行补出“信息复杂、容易拥挤、关系不清”等材料未提及的问题

4. **待确认失败项**
   - 出现交互样式、只读态、提示方式、承载形式、按钮摆放等设计师可自行出方案的问题
   - 出现后续会议、更新材料或用户补充中已有答案的问题

5. **设计目标失败项**
   - 同一页面 / 弹窗 / 抽屉 / 流程节点被拆成多个同级目标
   - 明确点名的子能力在合并后丢失
   - 为了塞入多个模块而形成难读的长句，却没有保留一句概括并用二级 bullet 展开
   - 二级 bullet 新增了范围，或把外部入口、返回路径误写成页面 / 模块内部组成

6. **整体失败项**
   - 把材料未明确说明的内容补成事实
   - 同一信息在多个章节重复
   - 输出像会议流水账，而不是设计 briefing

## 执行前必须读取以下文件

在开始处理任何材料之前：

1. 读取 `rules.md` — 处理规则、输出风格、主语要求和各章节细则
2. 读取 `templates/requirement-brief-html.md` — `design-requirement-brief-[需求名].html` 的输出结构、HTML 样式要求和输出前检查清单
不得跳过上述步骤直接输出。
