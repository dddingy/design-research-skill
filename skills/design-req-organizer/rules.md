# 处理规则

## 基本处理原则

- 语音转写稿的口语化表达、重复确认、说话人标注、时间戳等格式噪音，自动忽略
- 忽略闲聊、重复讨论、与设计无关的内容
- 某项信息材料中未提及时，写「材料中未提及」，不自行补充
- 只写材料明确说明的内容：原文直接说了，或能被稳定复述；不要自行补全
- 不要把设计建议、体验判断或常识推断写成材料事实；如需表达，只能写成「可探索方向」，且必须绑定材料中明确出现的功能或规则
- 未定的产品口径不要包装成设计重点：命名、最终入口、权限边界、必填字段、状态判定责任等，只要需要 PM / 业务 / 研发拍板，就放「待确认问题」；不要改写成「设计需保持弹性」「信息架构需中性」「可探索承载方式」
- 输出层级必须来自材料本身：材料只有事实就只做事实归纳，材料有流程才写流程，材料有设计取舍才写设计重点，材料有多页面 / 多容器才拆多个页面 / 容器；不得因为模板存在而补出材料没有的信息层级
- 模板不是填空题：没有材料支撑的模块、表格、策略、机会点、wireframe 或字段清单，不得为了完整性扩写；不能用“提升感知、优化体验、形成闭环”等泛化设计语言填充空模块
- 不要照搬说话人口吻，要把原始讨论翻译成产品语言
- 平台内专有名词、页面名和内部模块名优先保留原词；只有当原词明显是语音转写误差、临时口语指代或会影响读者理解时，才补充一句解释，不要擅自改名
- 优先按"模块"或"设计决策"合并信息，不按原始发言次数拆分
- 完整不等于逐条罗列；同一页面、同一功能、同一约束主题的信息必须先归并，再输出成少量高质量条目
- 合并信息不能丢失关键子能力：如果一个模块包含多个被点名的功能、状态、角色、上下文或不同规则，必须先列出子能力，再做归纳
- 同一信息只能放在最能指导设计的位置，不要为了"完整"在约束、重点关注、结论、待确认中重复出现
- 如果一条信息同时包含"系统内部规则"和"是否外显/怎么呈现"，先分别判断：已确认的内部规则进入约束或结论；只有材料明确指出外显方式存在具体设计难点及影响时，才进入设计重点关注
- 如果多个子功能都发生在同一页面或同一流程内，优先挂到该页面 / 流程下合并表达，不要为了功能名不同拆成多个顶层模块
- 输出前必须先做「设计对象合并」：同一页面 / 弹窗 / 抽屉 / 流程节点只能作为一个独立设计目标；需求对象也可以只是页面内的一个模块，不要求“页面”才是顶层目标
- 合并前先识别设计对象的主内容、用户操作、状态反馈和真实内部组成。外部入口、来源场景和返回路径不属于页面内部模块，应放在「使用场景与入口」或最相关章节中单独说明
- 默认用一句话概括一个设计目标。只有一句话因包含多个明确模块 / 能力而难以阅读时，才保留一句概括，并用二级 bullet 展开组成部分；二级 bullet 只用于提升可读性，不得新增范围或拆出新的设计目标

## 页面信息完整性预检查

在分类前，必须先识别材料中出现的页面、弹窗、抽屉、Review、创建流程等设计对象。

每个设计对象先内部检查信息是否完整：
- 页面 / 流程节点展示什么内容
- 用户在页面完成什么判断或操作
- 页面包含哪些被明确提到的功能模块、辅助入口、状态反馈和后续流向
- 如果材料中存在对象之间的关系（例如推荐、关联、配置、创建、归属、分组），是否说清「哪个对象」和「对应的另一个对象」是什么
- 如果页面中同时存在主任务和辅助能力，必须先判断辅助能力是否仍发生在该页面；是则并入该页面职责，不得因为不是主流程而遗漏
- 入口从另一个页面 / 场景发起、操作后返回原任务时，它是外部使用场景与路径，不是当前页面的内部模块

这一步是完整性检查，不是固定句式要求。只有当材料明确存在对象关系时，才需要在输出中保留关系；不要为了套规则把简单页面写复杂。

校准示例：
- ❌ `结果页中，展示推荐项。` / `筛选区中，支持筛选。` / `状态提示中，展示未完成状态。`
- ✅ `结果页中，列出系统建议处理的对象及推荐原因；用户可筛选、选择处理项，并进入后续确认流程。`

## 功能说明压缩规则

本技能只生成给人阅读的 `design-requirement-brief-[需求名].html`。

### design-requirement-brief-[需求名].html：简洁准确

给人看的 HTML brief 不输出功能说明表、字段清单或逻辑模型。每个功能只写成 1 句高密度功能句，最多 2 句，并通过 HTML 卡片 / 表格 / 标签提升可读性。

HTML brief 的加粗必须克制：
- 设计目标：每条只加粗开头的设计对象，不在句中继续加粗
- 设计重点关注：每条只加粗开头的关注主题，建议使用「主题：」格式，不在句中继续加粗
- 约束条件、设计结论、待确认问题：只加粗短关键词、关键状态或规则结果；避免整句、半句、解释性短语加粗
- 同一条内容原则上只保留 1 个主要加粗块；确有并列状态时最多 2 个

HTML brief 的正文必须压缩：
- 设计目标每条写「对象 + 承载内容 + 用户动作 / 结果」，不要展开推理过程
- 设计重点关注每条写「问题主题 + 需要设计处理的矛盾」，不要写成长段分析
- 删除不会改变设计判断的解释性补语，例如「为了保持弹性」「避免过早锁死」这类包装语
- 优先用白话说明「从哪里进入、看到什么、能做什么、操作后发生什么、看完回哪里」；少用「承接、复用结构、返回上下文、链路」等抽象表达

写句子前先在内部识别功能的 5 个要素：
- 承载位置：在哪个页面 / 弹窗 / 模块里
- 用户动作：用户能做什么
- 系统反馈：提交后页面展示什么、谁能看到、状态如何变化
- 生效范围：个人 / 项目 / 团队 / 单个对象 / 对象 + 类型
- 未定边界：入口位置、展示权重、权限、粒度等哪些还没定

最终压缩成一句：

`[页面/模块] 需要提供 [功能入口/能力]，用户可 [动作]；[结果/可见范围/状态]，[未定边界如有]。`

示例：
- ❌ `模板用于提升生成准确性。`
- ❌ `模板功能包括上传文件、选择项目、查看、更新、生效范围、入口位置。`
- ✅ `报告生成页面需要提供模板入口，支持上传模板文件并选择项目；同项目成员可查看 / 更新，生成结果会参考该模板。`

如果材料明确在某页面语境中讨论某功能，即使页内位置未拍板，也要写成：

`[功能] 承载在 [页面/容器] 语境中；页内具体位置 / 展示权重待设计。`

不要把这种情况降级成笼统的 `入口位置待定`。

## 输出风格

- 输出应接近设计师开始画方案前会看的整理结果，不是分析过程
- 默认追求"信息足够、表达简洁"，不要把一句话写得过满
- HTML brief 中的设计目标和设计重点关注应优先短句表达；每条通常 1 句，信息过密时最多 2 句
- 语言要像给设计师的 briefing，避免口语化复述，避免写成“有人提到”“讨论了”这类弱表述
- 能明确就不要写模糊词，能落成设计任务就不要停留在背景描述
- 如果材料已能支持明确判断，直接下结论，不要机械写「待确认」
- 输出密度以"设计师读完能开画"为准；优先给出功能定义、页面承载、关键规则和未决问题，避免把内部推理过程写成报告

---

## 🔒 主语规则（设计结论和约束条件每条必须套用以下句式之一）

✅ 允许的主语格式：
- `[页面名]中，[动作/规则]`
- `首期方案不支持 [具体功能]`
- `系统在 [条件] 下，[行为]`
- `仅 [角色] 可以 [操作]`
- `[功能名] 入口不能放在 [位置]`
- `[模块名] 需要 [设计要求]`

❌ 禁止出现的主语或指代词：这里、这个、它、这样、后面

## 各章节处理细则

### 背景
- 背景优先写成 2 句：第一句说明产品 / 业务对象的基本作用，第二句说明本期要设计的具体功能、核心流程和不包含的范围
- 本期功能定义必须具体到"系统做什么、用户做什么、后续接到哪里"，不能只写业务目标或抽象能力
- 如材料提到 PM Demo、目标上线时间、发布范围、项目阶段，可并入第二句末尾；不要另起长段
- 如果会议同时提到"大方向"和"当前版本"，以"当前这次要做什么"为主
- 不要把其他材料中的业务数据、平台指标、市场案例自动补进背景
- 背景过长就压缩，背景不是主体

### 设计目标
- 每条目标对应一个独立设计对象，可能是页面、弹窗、流程节点，也可能只是页面内的一个模块；优先写清对象任务，不要只写"设计 XX 的交互逻辑"
- 页面类目标要写清页面展示内容、用户动作和关键模块；如果材料中存在对象关系，再补清对象之间的推荐、关联、配置、创建或分组关系
- 同一模块、同一层级、同一轮交付的内容优先合并成一条
- 会议里反复讨论的关键页面，必须总结"该页面包含哪些功能模块"，不能因为某模块不是主流程就省略
- 会议里反复讨论的核心能力，如果包含多个明确命名的子功能，不得只写模块总称；必须在目标中点名这些子功能
- 设计目标默认用一句概括。只有一句话因包含多个明确模块 / 能力而难以阅读时，才在概括下使用二级 bullet 展开；二级 bullet 只说明真实组成部分，不新增范围
- 设计目标中不得出现多个条目指向同一个页面 / 弹窗 / 抽屉 / 流程节点；如果出现，必须合并为一个条目
- 某个模块有独立确认流程、配置展示或状态反馈，应单独成条
- 外部入口、来源场景和返回路径不属于页内模块，不得放进页面目标的二级 bullet；需要保留时放入「使用场景与入口」、5W1H 或对应结论
- 禁止空泛目标：`设计 XX 的交互逻辑`、`设计 XX 的承载方式`、`设计 XX 的体验优化`，除非同一句补齐页面内容、用户动作和功能模块
- 不要把发布排期、负责人写进设计目标

### 用户与影响范围
- 不得根据功能自行虚构或拆分用户类型；只写材料明确出现的角色、范围
- 优先写成一段收敛表达：先说"这个功能面向谁"，再补"当前覆盖哪些范围"
- 权限表述优先保留会议里的直接说法，不要改写成另一套体系
- 对材料未提及的权限层级，不要写成具体用户类型

### 设计重点关注
- 只收录材料明确提出、且设计师可以通过方案探索解决的真实设计难点；不收录需要 PM / 研发补规则的问题
- 每条必须同时写清：具体对象 / 场景 + 设计难点或矛盾 + 对理解、判断、操作、流程或状态的影响
- 多个候选方案、个人建议、倾向或参考方案本身不构成设计重点；材料没有说明难点和影响时直接省略，不替材料推断
- 不要写成空泛概括，如"需要提升感知""需要优化体验"
- 不要使用材料未明确支持的体验判断，如"关系需要更清晰""信息密度较高""容易拥挤"；除非材料明确说了看不懂、感知不到、不好放、不好看、信息多、复杂等问题
- 对有明确上下文差异的功能组，必须按功能逐项写清：全局可用、依赖页面、自动填充、降级提示、触发结果差异
- 适合放这里的内容：材料明确指出用户难以感知入口前置条件、窄面板信息过多、只读态容易误解或操作反馈不完整等具体问题
- 对"系统已确定会使用，但是否展示给用户未定"的信息，只有材料明确说明该取舍形成设计难点及影响时才进入设计重点关注；否则不输出

### 设计约束条件
- 每条改写成"规则句"，像产品约束而不是会议记录
- 每条末尾标注来源（说话人或角色）
- 前后矛盾时，在该条末尾注明「⚡存在矛盾」
- 必须先按主题分类，再写约束；常见主题包括：本期范围、权限与可见范围、系统计算 / 保留规则、创建 / 提交流程限制、安全合规、跨端 / 平台限制
- 同一主题（同一 token 规则、同一权限模型、同一首期 scope、同一入口提交规则、同一可见范围）必须合并后再写
- 一个功能的提交方式、生效范围、可见范围属于同一约束主题时，合并成一条；不要拆成多条相邻约束
- 一个主题下如果有多条材料事实，优先合并为 1 条复合约束；只有当规则会影响不同设计决策时才拆开
- 不要把协作闲聊、研发实现波动、还原度担忧、前端按稿配合方式写进约束条件
- 「研发 effort 大」不自动等于技术限制；只有材料明确说研发确认做不到、平台不支持或本期无法实现，才进入约束条件

### 设计相关结论
- 只写有决策权的人已经明确拍板或排除、且未被后续材料推翻的结论；仅有人倾向、有人提议、给出参考或允许尝试，不能写在这里
- 每条末尾标注来源（说话人或角色）
- 不与约束条件重复列
- 必须按页面 / 功能 / 模块分组输出；优先使用材料中的真实对象名称作为分组名，如 `Agent 面板`、`快捷功能区`、`分享页`、`操作确认卡片`
- 同一分组下只放属于该页面 / 功能 / 模块的结论；不要按会议发言顺序混排
- 多句讨论共同指向一个明确方案时，合并成一条高质量结论
- 若多条结论本质上描述同一设计对象，合并为一条更完整的结论
- 结论优先挂载到页面：`推荐结果页中...`、`Preview 中...`，而不是只写抽象产品逻辑
- 页面类结论需要检查是否遗漏对象关系；如果材料明确提到「给 A 推荐/关联/创建 B」或「A 归属/拆分/分组到 B」，输出中要保留这层关系，不要压缩成泛泛的列表描述
- 页面类结论应尽量覆盖：页面内容、用户动作、关键辅助模块、后续流向；但避免塞入过多解释，优先用准确短句
- 入口、上传、查看、更新、状态提示等子能力，如果会议语境是在某个页面里讨论，必须归到该页面分组下；不要因为子能力名称独立就单独拆分组
- 同一子能力同时有"位置"和"展示权重"讨论时，写在同一页面分组下，合并成相邻或同一条结论
- 同一页面下的列表、筛选、入口、状态、辅助操作等，优先合并为能描述页面职责的 1～3 条结论；不要拆成字段清单
- 如果某页面存在多个明确子能力，第一条结论必须写成覆盖式页面职责句，包含所有关键子能力；后续结论只补充规则差异，不重复拆列表
- 判断规则：
  - "外部条件导致不得不这样" → 约束条件（不是结论）
  - "讨论后主动决定这样做" → 设计结论 ✓
  - "还在比较方案 / 只是有人提出" → 普通设计选择则省略；需要外部拍板且影响设计推进时才进入待确认

### 交付内容与时间节点
- 按协作节点合并，不按页面、模块、功能点机械拆分
- 同一负责人、同一截止时间、同一保真度的一组设计范围合并为一个交付物
- 时间优先保留原文节奏，如「当天内」「今天下午」「五一前」；能推断近似日期时可在括号补充
- 格式 / 保真度只有材料明确时才输出；无法确定就删除该列或字段，不写「待确认」
- 会影响交付节奏的时间信息（请假、节前 review、开发启动节点）在表格后补「注」
- 交付物名称要具体，不要只写「初稿」「终稿」，应补齐覆盖范围或用途

### 待确认问题
- 只保留设计师需要知道答案才能推进设计的问题
- 只列需要 PM / 研发 / 业务给外部答案的问题
- 以下不列：交互样式、显隐策略、只读态、承载方式、成功/失败/取消反馈（这些是设计方案要解决的）
- 以下不列：材料中已有明确答案的问题、与设计执行无关的技术选型
- 输出前逐条扫描后续会议、更新材料和用户补充；已有答案的内容移入对应约束或结论，不保留旧问题
- 不强制凑数量；真正阻塞设计的问题少于 4 条时，以高质量为准
- 每个问题后可补一句：为什么它会影响设计决策


### 建议竞品调研关注点
- 固定作为 `design-requirement-brief-[需求名].html` 底部章节输出，并在该章节内嵌入 `可选下一步：feature benchmarking`
- 本章节只是需求整理后的轻量调研种子，不是完整竞品调研计划；优先减少而不是扩展调研范围
- 基于当前需求本身提炼，不照抄用户原话作为固定模板，不写外部产品事实或竞品结论
- 先写 1 条最值得 benchmark 的主路径或关键设计问题；主路径应尽量串起触发条件、系统判断、用户查看、用户操作、确认和结果反馈
- 再列建议优先调研点，默认 1 条，必要时 2 条，复杂需求最多 3 条；只有当调研主题明显不同、后续需要不同截图证据时才拆开。调研点必须能作为 feature benchmarking 或 Canvas 的一行横向比较主题，不按页面、字段、按钮逐项拆分；相邻页面或动作服务同一个判断时必须合并成一条
- 每个调研点必须能指导下一步 benchmark 搜集截图或拆解交互，不写空泛体验词，也不要为了凑数量硬写；如果一个点只能作为单页面细节、字段问题或按钮位置问题，不能独立做横向对比，应并入更大的调研主题

### 可选下一步：feature benchmarking
- 固定放在「建议竞品调研关注点」section 内，作为关注点列表后的可复制模块
- 可选下一步模块必须是可复制的下一步输入草稿，建议用 textarea 承载，并提供“复制/选中”按钮
- 可选下一步模块只从当前需求和建议调研点中抽取信息；不写竞品结论、不写外部产品事实、不写候选产品或样本范围
- 必须包含：调研对象、1-2 个可横向比较的重点、输出要求
- 用户、场景、主路径、排除范围仅在会改变样本选择或调研范围时保留；主路径只用于多步骤流程
- 页面型需求默认只设一个调研主题，不按页内模块拆分方向
- 默认不超过 4 个有效行、约 150 字。删除某一行不影响样本选择时删除；与上方关注点重复时合并
