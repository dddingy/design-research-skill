# Design Definition Skill

把前置输入转成可进入设计评审与后续设计生成的设计定义产物。该 skill 不整理原始会议材料，不做竞品调研，只负责组织前置材料中已经明确的需求事实、流程、约束和竞品洞察，讲清楚这个需求在做什么、为什么做、怎么流转，以及下游 AI 生成设计稿需要遵守什么。

## 🔒 材料事实优先

本 skill 的第一原则是：按前置材料整理，不自行拓展内容。

- 每一句正文都必须能追溯到结构化需求文档、AI Design Input 或竞品报告中的明确内容。
- 不新增材料未明确表达的设计策略、机会点、风险判断、体验原则或方案建议。
- 不把普通字段规则、流程步骤或技术约束包装成“设计机会”“设计重点”“策略方向”。
- 模板控制结构，不控制内容量；不得因为模板有某个 section，就为该 section 硬生成内容。
- 语言必须简洁准确，优先短句；能用一句说清楚，不拆成多条扩写。
- 如果删除某句话后不影响读者理解需求事实、流程或约束，应删除。


## 评审文档边界

`design-definition-[需求名].html` 只服务 PM / 设计评审，提炼背景、目标、主流程、关键约束和设计关注点。已有 AI Input 仅作为事实输入；不得把其字段清单、状态规则或对象关系逐条搬入 HTML。

## 自适应评审密度

Design Definition 不使用固定条数或固定字数控制篇幅。需求复杂度由材料中的独立设计对象、任务路径、角色、状态和真实设计取舍决定；简单需求自然短，复杂需求允许展开。

生成正文前，先在内部建立“内容归属表”，不写进 HTML：

1. 提取评审必须知道的独立事实与设计判断。
2. 为每项指定唯一主章节：背景原因归 `Project Background`，设计对象与职责归 `Design Goal`，任务推进或页面组织归 `User Flow`，真实取舍归 `Design Focus`。
3. 同一事实在其他章节只有产生新的评审判断时才可再次出现；仅换一种说法、换一个章节视角或增加完整感，不构成新信息。
4. 从最小可评审版本开始。只有删除某项会让评审者无法理解范围、流程、状态或设计取舍时，才保留或展开。

完成初稿后必须做一次跨章节压缩：

- 对比 Header summary、Background、Scenarios、Goals、User Flow、Design Focus。
- 合并同一页面、容器或任务下的重复描述。
- 删除已经由页面结构、流程节点或表格清楚表达的正文复述。
- 保留评审判断，不保留为了证明材料完整而重复出现的事实。

## 输入

必须至少提供：
- `结构化需求文档`：来自 `design-req-organizer`，通常为 `design-requirement-brief-[需求名].html`，重点读取背景、设计目标、用户与影响范围、设计重点关注、约束条件、设计相关结论、待确认问题。若历史项目只有 `design-requirement-brief.html` 或 `design-requirement-brief.md`，可兼容读取，但新流程优先使用带需求名后缀的 HTML。
- `AI Design Input`（可选）：由 `ai-design-input` 生成；存在时读取其中的硬逻辑，不存在时不阻塞本技能。
- `竞品分析输入`：来自 `feature-benchmarking-skill` 的竞品分析报告，或固定占位 `本次跳过，无竞品报告`；同时结合 `01_benchmark_report.html` 与 `products/{product}.html` 核验证据。

如果已有结构化需求材料，可直接作为输入；如果只有原始会议记录、聊天记录、语音转写稿或讨论稿，先执行 `design-req-organizer`；两者都没有才要求用户补充。缺少 AI Input 或竞品分析都不阻塞本技能，后者按“本次跳过，无竞品报告”处理。

## 默认产物

默认只输出一份设计定义文件：

1. `design-definition-[需求名].html`
   - 给 PM / 设计看的设计说明文档。
   - 文件名必须包含当前需求名或项目名的 slug，并放在文件名后缀位置，例如 `design-definition-schedule-agent.html`、`design-definition-report-template.html`。
   - 只有当当前 workspace / project 明确只存在一个需求，且不会覆盖其他需求产物时，才允许使用 `design-definition.html`。
   - 主要场景是设计评审。
   - 目标是让评审者看完后清楚理解：需求是什么、核心流程是什么、材料已明确的关键约束是什么。

默认不生成 `ai-design-input-[需求名].md`。仅当用户明确要求生成、更新、补全 AI Input，或明确要求为后续 AI 生成设计稿准备输入时，才为缺失的 AI Input 调用 `ai-design-input`。若同一需求已存在 AI Input，设计定义阶段确认了会影响页面范围、对象关系、流程、状态、权限或操作粒度的逻辑变化，则必须自动调用 `ai-design-input` 同步更新；仅更新已确认变化，不重建或扩写其他内容。

没有阻塞问题时，最终回复只给生成 / 更新文件路径；如果用户明确要求直接输出源码，再直接贴对应文件内容。存在会影响设计定义的问题时，不生成 / 更新文件，直接在回复里列问题，等用户确认后再继续。

### 模板资源

执行本 skill 时必须先读取并使用同目录下的模板文件：

- `templates/design-definition.html`：生成 `design-definition-[需求名].html` 的固定 HTML 模板。必须先读取该文件，并以文件内容作为输出起点逐项替换占位；禁止凭记忆重写相似样式。必须沿用其中 CSS、基础信息顺序和正文 DOM 顺序，只替换占位内容，或在指定位置追加有材料依据的模块。User Flow 相关选择器是可选样式库，不要求每次使用同一种流程 DOM。

### 文件命名与防覆盖

- 开始输出前必须基于需求内容重新校准需求名；如果第一步需求名已经准确，就沿用相同 slug；如果第一步只是文件名、会议标题或临时叫法，必须重新总结更准确的需求名并使用新的 slug，同时避免覆盖旧产物。
- 设计定义 HTML 的默认文件名必须是 `design-definition-[需求名].html`，不要直接使用通用名 `design-definition.html`，也不要使用需求名前置的旧格式。
- 本技能只生成 / 更新 `design-definition-[需求名].html`；其他同名产物由对应技能维护。
- 同一个 workspace / project 里可能同时存在多个需求、多个 demo 或多个设计定义文件；生成前必须先检查现有 `*design-definition*.html`，避免覆盖其他需求。
- 如果已经存在 `design-definition.html`，先判断它属于哪个需求；除非用户明确要求覆盖，否则不要写入该文件。
- 如果用户或历史流程仍需要通用入口，可以在确认不会破坏已有文件后再创建跳转页；跳转页也不能覆盖其他需求的真实设计定义内容。
- 最终回复必须返回带需求名的实际产物路径。

## 职责边界

- 从需求中提取：目标用户、产品定位、核心任务、关键流程、限制条件、设计对象、待解决问题。
- 从 AI Design Input 中继承：范围与权限差异、核心对象、对象关系、列表 / 推荐项粒度、页面 / 容器、主流程、必要分支、状态规则、生效范围、现有承接页和复用边界。
- 从竞品报告中提取：报告中明确写出的可借鉴模式、差异化机会和风险。未确认或未采纳的内容只能作为报告证据保留，不得写成设计事实或 Design Focus。
- 合并后只输出清晰的评审说明、流程说明、材料已明确的设计重点、版本边界和问题定义；没有材料支撑的部分不输出。
- 不整理原始会议材料。
- 不做新的竞品调研。
- 不生成最终 UI 方案细节，不直接替代后续设计稿。
- 不把竞品做法直接写成最终方案；只能写成参考、机会或策略依据。
- 不把竞品 insight 未经用户选择直接写入 Design Direction。若只有 Canvas Benchmark、没有 Checklist 采纳结果，不能默认全量采纳。
- 不虚构业务数据、提升比例、用户规模、上线时间；材料未提及时写 `待确认` 或 `材料中未提及`。
- 不改写 AI Design Input 中 Logic Model 的对象关系、粒度、状态规则和流程边界；如果为了评审表达需要收敛语言，也必须保持这些硬逻辑不变。
- 如果 Human Brief 与 AI Design Input 冲突，以 AI Design Input 的对象关系、粒度、状态和流程为准；会影响设计范围或流程判断的冲突必须在生成前向用户确认。
- 不处理原始材料里的指代不清、转写不清或主语不明问题；如果前置产物中仍存在这类问题，必须先向用户澄清，确认前不得把它收敛成设计定义事实。
- 不把不稳定术语二次标准化；人工纪要 / 截图 / 明确文字中的术语优先于语音转写，无法判断时先问用户。

## 🔒 输入理解澄清闸门

生成 `design-definition-[需求名].html` 前，必须先检查结构化需求文档和 AI Design Input：

- 如果出现“这个 / 那个 / 它 / 这里 / 后面 / 这块 / 那块”等指代，且无法唯一判断对象，先在回复里问用户确认；这类澄清问题不能写进最终产物。
- 如果字段名、对象名、页面名、状态名、技术口径来自不稳定语音转写，且会影响对象关系、流程、字段、权限或生效粒度，先问用户确认；确认前不得写成设计目标、约束、流程或 Logic Model。
- 如果人工纪要 / 截图与语音转写冲突，以人工纪要 / 截图为准；仍无法判断时先问用户。
- 业务规则未定、范围未定、字段确实未定、权限未定等会阻塞设计定义的问题，必须在生成前直接回复用户并暂停；不要沉淀到 HTML 或 AI Design Input。
- 第三步产物是评审和存档用的设计说明文档，不输出“待澄清问题 / 待确认问题 / Blocking Open Questions”模块。

## 生成设计方案前置规则

当用户要求“生成设计方案 / 生成设计稿 / 出方案 / 做页面 / 做 demo / 继续画方案”时，先判断当前已经完成到哪一步：

1. **只有第一步产物时**
   - 如果只有 `design-requirement-brief-[需求名].html` 和 / 或第一步基础版 `ai-design-input-[需求名].md`，必须先自动执行本 skill 的第三步。
   - 先生成 `design-definition-[需求名].html`，再进入设计方案生成。
   - 不要直接只用第一步产物生成设计方案，因为会缺少设计定义、范围收束、策略和评审视角。

1A. **只有原始材料时**
   - 如果用户只有会议记录、聊天记录、语音转写稿或讨论稿，必须先自动执行 `design-req-organizer` 生成第一步产物，再执行本 skill。
   - 如果用户提供的是已经整理过、等同第一步的结构化需求材料，可直接作为结构化需求输入，不必重复跑第一步。

2. **第三步已完成后**
   - 在使用 `ai-design-input-[需求名].md` 生成设计方案前，必须先检查其中的 `Blocking Open Questions`、`Scope & Roles`、`Page / Container Map`、`Logic Model` 和 `States, Actions & Rules`。
   - 只筛选会实质影响方案结构、页面范围、流程分支、状态表达、权限范围、创建 / 提交粒度或高风险操作的问题。
   - 如果存在这类未确认问题，先问用户：“以下问题会影响方案，我可以先按默认假设推进，也可以等你确认”，并列出问题。
   - 用户可以逐条回答，也可以明确让 Codex 自行选择合理方案继续。
   - 如果未确认问题只影响文案、视觉样式、按钮位置、普通布局表达或设计师可自行探索的承载方式，不需要阻塞，直接由 Codex 做方案假设并继续。
   - 如果没有会影响方案结构的未确认问题，不要询问用户，直接生成设计方案。

## HTML 设计说明文档

HTML 是给 PM / 设计做设计评审用的。它的第一目标不是“信息完整”，而是“看完立刻懂这个需求在做什么、怎么走、设计判断是什么”。

### 模板契约

生成设计定义 HTML 时，必须读取 `templates/design-definition.html` 并把它当作固定模板，而不是风格参考。

允许变化：
- 替换项目内容、评分、链接、表格行、流程节点、设计重点。
- `User Flow` 内部可按需求生成单流程或多流程，也可在节点内增加与该页面直接相关的分支。
- 在必备模块之外，根据材料新增必要模块。

不允许变化：
- 不改整体信息顺序：`Review Header` → `Materials` → `Project Background` → `Design Goal` → `User Flow` → `Design Direction`。仅当用户明确要求 Wireframe / 线框图 / 低保真布局时，才在 `User Flow` 和 `Design Direction` 之间追加 `Wireframe`。
- 不换 CSS 视觉语言：深色通栏 header、白底单栏正文、分隔线、轻量表格、materials 标签、轻量流程 / 节点表达。
- 不改成 notepad、dashboard、showcase、卡片墙、左右分栏展示页或营销 hero。
- 不把示例内容、内部黑话或上一轮项目内容带进新项目。
- 不给无链接材料追加“可点击 / 待补充”等状态文案；只能通过可点击和不可点击样式区分。
- 不把没有页面承载的状态规则强行画进 User Flow。

输出必须是自包含 HTML：
- 完整 `<!doctype html>`、`<html>`、`<head>`、`<body>`
- 内联 `<style>`，不依赖外部 CSS、JS、字体或图片
- 内容画布必须沿用模板里的单栏平铺：`.hero-inner` 和 `main` 使用 `max-width: 1120px`
- 字体优先使用 `Inter, -apple-system, BlinkMacSystemFont, "Segoe UI", sans-serif`
- 通过标题、分隔线、留白、表格和轻量流程块组织信息
- 如果需要可视化，用 HTML/CSS 表格、步骤行、流程块表达；不要依赖 Mermaid CDN

HTML 不需要包含：
- `Version History`
- 面向开发或 QA 的详细交付说明
- 大段材料摘录
- 为了贴模板而堆叠的表格
- 与本需求无关的通用 UI 建议
- 没有材料依据、只为填满模板而生成的策略、机会点、范围矩阵或多余 wireframe

### 质量标准

优秀输出应该接近“设计评审说明页”，而不是“需求表格转写页”：
- 顶部用需求名、平台 / 子产品、需求类型和一句话说明需求主线。
- 先放材料、背景，再进入目标、流程、设计方向。
- `Project Background` 只补充评审需要的背景和场景；5W1H 与 Current Scope / Boundary 已前置到第一步需求整理，不在第三步重复生成。
- `User Flow` 只抽取 AI Design Input 中最能解释当前主设计对象的任务路径、页面结构或状态关系；字段清单、状态规则、权限细节、审批原因、对象关系和操作粒度留在 AI Design Input，不搬进 HTML。
- `Design Focus`、`Opportunity Mapping` 只在材料明确包含设计判断或机会映射时输出；不得从普通需求事实反推。
- 澄清问题不作为第三步产物模块输出；会阻塞设计定义的问题在生成前直接在回复里问用户。
- 表格只用于评分、材料、范围矩阵、机会映射等真正适合对齐的信息。
- 避免通用空话，例如“提升用户体验”“优化页面布局”“增强可用性”，必须写具体对象和路径。
- 输出层级必须来自材料本身：材料只有事实就只做事实归纳，材料有流程才写流程，材料有设计取舍才写设计重点；只有用户明确要求 Wireframe 且材料有多页面 / 多容器时，才画多个 wireframe。不得因为模板存在而补出材料没有的信息层级。
- 模板只提供可用容器，不是填空题；没有材料支撑的容器必须省略、合并或短写，不能用泛化设计语言填充。

## HTML 信息结构

默认顺序按当前设计评审页组织；若用户明确要求可调整内容模块，但不要回到复杂展示页风格。必备模块是模板骨架，不能省略。

现有核心模块是必须项，不能因为需求不同而省略。必须包含：
- `Review Header`
- `Materials`
- `Project Background`
- `Design Goal`
- `User Flow`，但内部结构必须按需求灵活生成，不固定为单流程或固定子标题
- `Design Direction`，内部只按材料明确内容输出 `Design Focus` 和 / 或 `Opportunity Mapping`；没有设计判断或机会映射依据时，不输出子模块，也不要写占位说明。

`Wireframe` 默认不输出。只有用户明确提出要 wireframe、线框图、低保真页面布局或类似表达时，才追加该模块。

默认结构是基线，不是上限。允许根据需求不同新增必要模块，例如：
- `Scenarios`：材料明确给了真实业务 / 使用场景。
- `Permission / Role Rules`：权限、角色、组织范围会影响体验。
- `State & Lifecycle`：状态本身有页面承载，且会影响用户判断或后续动作。
- `Content / Data Rules`：字段、排序、筛选、推荐理由、阈值等直接影响页面生成。
- `Integration / Entry Points`：存在多个入口、外部跳转、deeplink 或跨产品承接。
- `Risks / Trade-offs`：评审需要对齐高风险设计决策。

新增模块必须满足：
- 有材料依据，或明确标注 `待确认`。
- 能帮助评审或后续设计生成，不只是为了套模板。
- 不重复已有模块内容；如果只是已有内容的另一种说法，合并到现有模块。
- 放在最相关的位置，例如场景放在 Background，状态生命周期放在对应流程节点或 Design Direction。

### 1. Review Header

顶部必须快速说明项目和评审场景。

建议内容：
- 顶部信息行：只写大平台名、子产品名，不加 `平台：`、`产品：` 等标签前缀。大平台没有材料依据时写 `待确认`，不要把业务线或团队名误写成大平台。
- 主标题：`[Level] [Requirement Name]`，例如 `P1 Report Template Upload`。Level 是材料中给出的需求等级 / 优先级，放在需求名前，使用 `.title-level` 样式，只写等级本身（如 `P1`），不要写 `Level: P1` 或 `Level 待确认`；材料没有等级时省略 `.title-level`。
- 一句话 summary：讲清楚本需求聚焦的对象、动作和承接链路。
- 底部 meta：需求类型、适合设计评审 / 说明。

要求：
- `h1` 使用清楚的需求名，不要泛称“xx 功能设计定义”。
- summary 用 1 句话讲清楚这个需求在做什么。
- 大平台、子产品、需求类型均可来自材料；缺失时写 `待确认`，不要猜。Level 缺失时直接省略。
- 产品全名可放在顶部信息行的子产品位置；不要在 meta 中重复产品名。

### 2. Materials

必须输出 Materials。

要求：
- 有链接的材料用 `<a>`，无链接的材料用不可点击状态。
- 可点击 / 不可点击只用样式区分，不要在文本后追加“可点击”“待补充”。
- 推荐材料项包括：需求整理结果、AI Design Input、PRD 文档、Figma 设计稿、Feature Benchmarking Report。
- 没有竞品报告时，Materials 中只写 `Feature Benchmarking Report`，不要写“本次跳过，无竞品报告”，也不要在 Header 中展示竞品状态。

### 3. Project Background

用于补充背景，但不要压过流程和设计重点。

建议结构：
- 1 段项目背景：说明产品 / 子产品的现有场景和本需求所在位置。
- Project Background 需要让读者看完后能判断：
  - 这个需求发生在哪个产品 / 模块 / 页面语境中。
  - 用户原本在处理什么业务任务。
  - 本次新增或改造的设计对象是什么。
  - 该设计对象承接哪些核心动作、上下文或后续流向。
- 背景写法应根据材料自然组织，不要求固定句式、固定顺序或固定字数。
- 不要把“已有 demo / 需要优化 UI / 当前页面不好看 / 视觉不专业”作为背景主线；这类信息只能作为材料状态、交付参考或约束出现，不能替代业务任务和设计对象说明。
- `Scenarios`：只有当设计师、PM 或材料明确给了真实业务 / 使用场景时才写，放在背景里作为理解需求的上下文；没有明确场景时不要硬补。
  - 如果场景只是重复 User Flow 的入口、Design Goal 的对象或 Design Focus 的问题，不输出 Scenarios。
  - 只有场景会引入不同角色、不同任务结构、不同页面 / 状态或不同设计取舍时，才具有独立评审价值。
  - 先按 user type 分组：材料明确给出 user type 时，先写 user type，再写该 user type 下的一到多个 scenario；没有 user type 就直接写 scenario，不要补。
  - 每个 scenario 只写一句话，包含业务情境 / 触发原因 / 目标，例如“项目负责人收到异常告警后进入监控页查看失败任务”。
  - 不合格的 Scenarios：功能步骤、页面操作、筛选条件、流程节点、设计要求，例如“用户按名称筛选推荐项”“用户进入 Review 理解拆分任务”。这些应放在 User Flow、Design Goal、Design Focus 或 Opportunity Mapping。
- 第一阶段需求整理中已有 5W1H 和 Current Scope / Boundary 时，第三步不再重复生成；Project Background 只保留背景段落和必要 Scenarios。

要求：
- 必须来自结构化需求，不要扩写。
- 范围矩阵是可选结构，不是强制；如果材料没有明确版本 / 范围边界，就省略该模块。

### 4. Design Goal

按独立设计对象组织设计目标，不设固定条数。每条必须对应不同页面、容器、流程节点或具有独立职责的设计对象，并能指导后续方案生成。

要求：
- 不重复背景描述。
- Design Goal 需要对第一步目标做合并收敛；同一页面、同一流程或同一设计对象下的目标合并表达，不逐条搬运原始需求。
- 分区选择、指标展示、字段详情等能力如果都由同一个主页面承载，应合并进该页面的一条目标；只有独立容器、独立确认流程或独立状态反馈才单独成条。
- 页面类目标使用「页面职责 + 关键能力清单」写法：同一模块、同一层级、同一轮交付的内容优先合并；同一页面 / 弹窗 / 抽屉 / 流程节点不得拆成多个条目；材料明确命名的子功能必须在同一条中点名。
- 某个模块有独立确认流程、配置展示或状态反馈，应单独成条。
- 使用“设计对象 + 目标说明”格式，不使用“让用户……”“让页面……”句式；该句式只允许出现在 Design Focus。
- 每条建议格式：`<li><strong>[页面 / 模块 / 设计对象]</strong>：[本对象本次需要达成的设计目标]。</li>`
- 只写要设计什么、对象承担什么职责，不写设计策略、用户感知问题或机会点。
- 用具体对象和动作表达，例如推荐列表承载推荐项、Review 页面组织确认流程、创建入口接入现有页面。

### 5. User Flow

必须输出 `User Flow` 章节，但章节名不等于必须画线性流程。生成前先在内部判断本需求最需要表达的是：

- `task-flow`：用户为完成任务而执行的连续动作、分支或结果落点。
- `page-structure`：单个页面内部的信息层级、区域划分和主次关系。
- `state-relationship`：对象状态以及用户动作如何推动状态变化。
- `hybrid`：页面结构与必要动作关系都影响理解；只保留最小必要组合。

判断结果只用于选择表达方式，不在正式 HTML 中增加“AI 判断过程”、模式切换器，或“为什么采用页面结构 / 为什么不画连续流程”等生成说明。`User Flow` 标题下的引导文案必须描述当前需求中的用户任务、查看对象或结果，不得解释文档是怎么生成的。

`task-flow` 节点必须包含用户动作：输入、选择、上传、查看、确认、取消、返回、编辑、提交等。只解释功能、字段、模块或能力的节点不是任务流程节点。

`page-structure` 必须画得像低保真页面：包含接近真实页面比例的外框、顶部或侧边导航上下文、页面标题 / 操作区、筛选区、内容分区及其嵌套关系。不得用编号卡片、纵向箭头或模块关系图代替页面骨架；字段细节只保留到能帮助判断区域职责的程度。

`state-relationship` 使用状态节点与触发动作，不得把页面模块当状态。

#### User Flow 判断规则

仅当表达类型为 `task-flow` 或 `hybrid` 时，再判断材料表达的是“连续流程”还是“并列功能”。

- 先从整个需求语境里判断这个需求在解决什么用户问题，再提炼主流程。主流程是用户为解决该问题必须完成的关键动作链路。
- 先判断主设计对象，再判断入口数量。多个入口或业务场景最终进入同一个核心页面 / 容器、查看同一组信息并完成同一任务时，优先表达核心页面结构；入口只作为轻量入口说明，不展开成多条重复主流程。
- 只有入口后的任务目标、关键动作、页面承接或结果落点实质不同，才拆成并列任务路径。
- 用户必须按 A → B → C 的顺序完成，才画连续流程。
- 优先判断用户的主要任务顺序，再判断某一步内部是否有分支。
- 同一页面、面板或产品里的几组功能入口，没有强制先后关系，按并列路径分组展示，禁止用箭头串联。
- 材料里用 1、2、3 列出来，不代表是连续流程；要看用户是否真的必须按这个顺序完成。
- 基础功能只有在本需求需要定义它们时，才进入 User Flow；进入时只能作为并列路径，不要默认命名为“主流程”。
示例：
不这样做：打开 Agent → 新建会话 → 查看历史 → 快捷功能 → 操作确认 → 分享
这样做：会话路径 / 会话管理路径 / 快捷功能路径 / 操作确认路径 / 分享只读路径。

如果材料主要是权限、字段、生效粒度或后台规则，没有可表达的页面操作路径、页面结构或状态关系，放到相关约束或 `Design Direction`，不要用功能清单伪造 User Flow；无法判断时先向用户确认入口、动作、页面区域、状态或结果落点。

任务流程内容准入：
- 开头用一句话总结主路径 / 主场景。
- 每个节点默认是用户动作：输入、选择、上传、查看、确认、取消、返回、编辑、提交等。文案可省略“用户”；只有多角色流程或非用户执行节点，才在卡片前加角色 tag（如 Admin / AI / 系统）。
- 系统响应、分支条件、结果落点只能作为节点补充，不能替代用户动作。
- 分支条件只写会改变后续路径的条件。
- 结果落点只写用户到达的页面、容器、状态或对象变化。
- 只在解释功能 / 字段 / 模块 / 能力，且没有表达流程推进的节点，不是 User Flow 节点。

#### 材料不足时

如果材料无法支持明确的任务流程，先判断它是否实际属于 `page-structure` 或 `state-relationship`；只有三者都无法表达时，才向用户确认入口、动作、页面区域、状态或结果落点。不得用功能清单占位。

输出质量要求：
- 文字必须简洁，节点只写动作推进和必要结果，不写解释性长句；默认主语是用户，不要每句话都重复“用户”。
- 只画主流程和影响路径理解的必要分支；不要加入背景说明、功能解释、字段解释、规则解释等无关内容。
- 多并列主场景时，每个场景只写关键节点，不展开长说明。
- 分支 / 备注只在影响路径理解时输出，不强行加。
- 不为了视觉完整而强行编号、强行拆步骤、强行加分支。
示例：
不这样做：`首页 / 对象列表 / 创建入口 → 对象详情 → 结果对象`
这样做：`1. 进入总览 → 2. 查看列表（入口 A / 入口 B / 总览入口）→ 3. 创建记录 → 4. 进入详情 → 5. 查看结果`

User Flow 组件库可自由组合，不是互斥选项。一个 User Flow 里可以同时使用多个组件，按当前需求的流程结构自由拼装。先判断每段内容的结构特征，再选对应组件。

- 页面结构组件：复用模板 `.wireframe-page`、`.wf-title`、`.wf-toolbar`、`.wf-layout`、`.wf-panel`、`.wf-table` 等选择器，在 `User Flow` section 上标记 `data-user-flow-type="page-structure"`。页面结构型不得使用 `.flow-map`、`.lane-flow`、`.parallel-flow`、`.phase-flow` 或 `.handoff`。

- 组件 1：单一路径 `.flow-map` + `.flow-row` + `.flow-num` + `.flow-box`。节点是用户动作；用于固定顺序操作。节点是页面时改用 `.handoff`，有自然阶段时改用 `.phase-flow`。若“总览 / 列表 / 创建 / 详情 / 结果”等节点构成同一任务的必经顺序，即使中间存在多个入口或分支，也优先使用该组件；多入口只作为某个步骤里的 `.branch-grid`，不改变主流程结构。可在 `.flow-box` 内嵌套 `.branch-grid`。
- 组件 2：并列独立任务 `.path-grid` + `.path-card`。节点是独立场景摘要；用于多个入口不同、流程不相交、没有先后顺序的任务。有箭头和流转方向时改用 `.handoff`；每条路径内部需要展开短步骤时改用 `.lane-flow`。
- 组件 3：分组任务路径 `.lane-flow` + `.lane-track` + `.lane-card`。节点是路径内步骤；用于同一功能主题下有 2-3 条独立任务路径，每条路径内部有 3-5 个短步骤。路径只有摘要时改用 `.path-grid`；路径是完整主场景或有复杂角色协作时改用 `.parallel-flow`。
- 组件 4：多主流程展开 `.parallel-flow` + `.parallel-track` + `.parallel-step`。节点是流程内关键步骤；用于每个角色或每条主流程内部有多个关键节点要展开。只有标题摘要时改用 `.path-grid`；只有一条主流程时改用 `.flow-map` 或 `.phase-flow`。
- 组件 5：分阶段长流程 `.phase-flow` + `.phase` + `.phase-steps` + `.phase-step`。节点是阶段内用户动作；用于同一主流程有自然阶段划分。没有阶段时改用 `.flow-map`。
- 组件 6：决策分支 `.branch-grid` + `.branch`。节点是并列出口；用于同一决策点的选择会改变后续走向。可嵌套在 `.flow-box`、`.stage`、`.phase-step` 等容器内。
- 组件 7：页面 / 容器承接 `.handoff` + `.stage` + `.arrow`。节点是页面 / 容器；用于页面、面板、弹窗、抽屉之间的横向承接。节点是用户动作时改用 `.flow-map`。
- 组件 8：状态驱动流程 `.state-flow` + `.state-step` + `.state-pill` + `.state-action`。节点是对象状态；用于同一对象有明确状态流转，且每个状态变化有用户触发动作。
- 组件 9：自由画布流程 `.canvas-flow` + `.canvas-node` + SVG lines。节点是页面 / 操作节点；用于页面扇出多条操作路径、页面内 tab / 面板也要标注、或节点关系无法用线性组件清晰表达。节点坐标和 SVG 路径需要按当前需求手动计算。
- 组件 10：自行设计。以上组件都无法清晰表达当前流程结构时，根据内容自行设计 HTML 结构和 class，不为“有结构感”强行套组件。

输出前自检：
- 是否先判断 `task-flow / page-structure / state-relationship / hybrid`？
- 页面结构型是否真的呈现页面外框、布局区域和嵌套关系，而不是卡片加箭头？
- 组件选择是否从内容出发决定，而不是从组件库反推？
- 是否把并列主场景误画成了线性流程？
- 每个节点是否都有用户动作？是否有节点只是功能说明？
- 是否把字段、规则、页面能力塞进了节点？
- 节点文案是否足够短，能快速扫读？
- 分支 / 备注是否只在影响路径理解时才出现？

### Optional. Wireframe

默认不输出 Wireframe。只有用户明确提出要 wireframe、线框图、低保真页面布局或类似表达时，才输出该模块，用低保真页面布局草图帮助评审者理解当前需求真实涉及的页面 / 容器内部承载关系。它不是最终视觉稿，也不是把需求内容再写一遍。

Wireframe 和 User Flow 必须区分：
- User Flow 表达用户任务怎么走。
- Wireframe 表达每个关键页面 / 容器里有哪些区域、信息和操作。
- Wireframe 不是流程图，不要用箭头把页面串成流程；如果需要表达跳转关系，放在 User Flow。

生成前先判断：
- 当前需求涉及几个页面 / 容器：主页面、侧边面板、弹窗、抽屉、确认卡片、Review / Preview 容器、现有承接页等；只能根据材料选择，不要把模板或上个项目当成必备页面。
- 哪些页面是本次要重点设计，哪些只是上下文来源或复用承接。
- 是否有明确状态切换，例如 empty / welcome、active、review、confirmed 等；状态名称必须来自当前材料或当前页面语义。
- 哪些动作会触发页面 / 容器切换，例如输入、选择、查看、确认、提交等；具体动作名称必须来自当前材料，不要沿用上一个需求。

推荐规则：
- 如果只有一个主页面 / 容器，输出一个完整页面 wireframe。
- 如果有多个页面或容器，且用户已明确要求输出 Wireframe，必须给多个 wireframe；每个 wireframe 画对应页面内部布局，不要只画页面名称和流转关系。
- 主设计对象必须占视觉主导；上下文页面、复用页面或非本期重点页面要弱化和简化，只保留必要位置与关系。
- 注意页面内容主次：只展开和当前需求直接相关的区域；不涉及需求的导航、列表、详情区、背景页面内容尽量简化成占位或一句上下文说明。
- 页面比例要接近真实承载环境，例如浏览器页面用接近 16:9 的画布，右侧面板按真实窄面板比例表达。
- 如果状态变化会影响理解，可以做成简单状态切换；但不要为了套模板强行做交互。
- Wireframe 的视觉语言要和正文表格区分，可以使用轻微底色、虚线、草图感边框；但不要用粗边框、大面积高饱和色或装饰性图形。
- Wireframe 内文案只写结构标签和关键状态，不展开长需求说明；详细说明放到 Design Focus 或 Opportunity Mapping。
- 不要把单个需求里的事实抽象成通用规则。例如某需求里某个动作只是对话内动作，不代表所有需求都要把它当作页面、功能或固定模块。

### 7. Design Direction

`Design Direction` 是模板骨架，不是内容扩写入口。只有前置材料明确包含设计判断、取舍、策略、竞品启发或机会点时，才在其中输出对应子模块；否则保留结构但不生成子模块内容，也不要写“暂无”“本次未沉淀”等占位说明。

#### Design Focus

只有材料明确表达设计难点、取舍、风险或降噪问题时，才输出 Design Focus；没有就不输出该子模块，不按固定数量凑内容。

要求：
- Design Focus 只写材料明确表达的设计难点，不写基础事实，不从普通流程、字段或约束中反推设计重点。每条输出前在内部自检：材料是否已经表达了取舍、优先级、复杂承载、风险或降噪问题；如果没有，就不要写入。
- Design Focus 不设固定条数。每条必须对应一个不可被其他条目替代的设计取舍；同一理解问题在不同页面或字段上的表现应合并，除非需要不同设计决策。
- 如果某条只是重复 Background 中的问题、Design Goal 中的页面职责或 User Flow 中已经清楚表达的动作，应从 Design Focus 删除；只有补充“为什么难、需要在哪个设计落点做取舍”时才保留。
- 如果没有任何符合条件的设计难点，省略 `Design Focus`，不要写“暂无”或占位说明。
- 必须用“让用户……”或同等完整句式写成可读句子，不用抽象短标签当主表达。
- 每条格式建议为：`<li><strong>让用户[理解 / 判断 / 选择 / 区分 / 控制 / 找到]...</strong>：[具体设计落点]。</li>`。
- 加粗部分写设计要解决的用户理解 / 行动问题，不写页面名、功能名或重复前缀。
- 冒号后写设计落点：在哪个页面 / 容器、呈现什么信息、支持什么操作、避免什么误解。
- 写具体设计对象，不写泛泛原则，例如不要只写“推荐理解”“选择效率”“状态可信”。
- 每条都必须来自材料中的明确设计判断，并能指导后续设计稿。
- 如果原始材料只有内部黑话或短词，保留必要术语，但要转成参会者能读懂的完整句子。

示例：
- `<li><strong>让用户知道为什么要处理</strong>：每条推荐必须解释推荐原因，帮助用户判断是否处理。</li>`
- `<li><strong>让用户能快速挑出要一起处理的项</strong>：推荐列表需要支持名称、负责人、项目、类型、推荐原因等筛选。</li>`
- `<li><strong>让用户理解为什么会被拆成多个创建任务</strong>：Review 要讲清按项目 + 类型的拆分规则。</li>`

#### Opportunity Mapping

只有材料已经明确表达“问题 / 约束、对设计的影响、设计机会”三者关系时，才输出机会点映射。

不得从普通约束、流程或字段规则反推 Opportunity Mapping。

竞品 Insight 可以成为 Opportunity Mapping，但必须满足采纳门槛：它来自 Canvas Benchmark 的证据，并已在 Design Reference Checklist 中被用户勾选，或用户在对话中明确说采纳该条。未经选择的竞品 insight 只能留在 Benchmark / Checklist，不能进入正式 Design Definition。

建议表头：
- `问题 / 约束`
- `对设计的影响`
- `设计机会`

没有竞品报告时，不强行写 `Benchmark Insight` 列。

### 8. 澄清问题处理

本章节不输出澄清问题、待确认问题或 Blocking Open Questions。具体澄清条件以“输入理解澄清闸门”为准；只影响后续方案探索、而不影响范围或流程判断的问题不阻塞本产物。

### Logic Integrity Gate

输出 `design-definition-[需求名].html` 前必须检查：

- 核心对象是否完整继承自 AI Design Input 的 Logic Model。
- 列表 / 推荐项 / 卡片 / 任务组的最小粒度是否明确。
- 一对多关系是否保留，没有被合并成单一父对象。
- 页面 / 容器地图是否保留，特别是入口页、主处理页、Review / Preview / 确认容器、现有承接页。
- 状态和操作的生效粒度是否明确，例如按用户、按项目、按单个对象、按对象 + 类型。
- 现有承接页是否被标注为复用，没有被生成成新的主页面。
- 未来扩展入口是否与当前版本主入口区分。
- 如果某项缺失，只能写 `材料中未提及` 或 `待确认`，不能自由补成事实。

## HTML 视觉建议

默认采用简洁评审文档布局：
- 必须使用 `templates/design-definition.html` 中的 CSS。除非用户明确要求换风格，否则不要重写一套新的视觉样式。
- 重点标注只加粗动作、状态、对象粒度、范围差异；不要反复加粗每条都重复的页面名或小节标题。
- 表格只用于 Opportunity Mapping 等适合对齐的信息；Materials 使用标签列表。

## 输出原则

- 先用评审视角讲清楚需求主线，再补背景和依据。
- HTML 面向 PM / 设计评审，强调“需求是什么”“流程怎么走”“设计重点和边界是什么”。
- 正文可用中文，关键章节标题可保留英文。
- 输出是可直接打开的设计评审 HTML，不写成聊天式解释。

## 生成前检查

写入 `design-definition-[需求名].html` 前必须自检：
- 是否保留模板 CSS 的基础视觉系统；User Flow 相关选择器是否只作为可选样式库，而不是强制 DOM 模板。
- Header 是否是深色通栏，顶部信息行是否只写大平台和子产品，h1 是否为 `[Level tag] + [Requirement Name]`（无等级时只写需求名）。
- 正文顺序是否为：Materials、Project Background、Design Goal、User Flow、Design Direction；若用户明确要求 Wireframe，是否放在 User Flow 与 Design Direction 之间。
- Materials 是否用 `<a>` 表示可点击材料、`<span>` 表示不可点击材料，且文案里没有“可点击”“待补充”。
- User Flow 是否按本节判断规则选择结构，且状态 / 规则只放在相关节点或 Design Direction 中？
- Project Background 是否讲清产品 / 模块 / 页面语境、用户业务任务、本次设计对象和核心承接动作；是否避免把 demo 状态、UI 优化诉求或视觉评价写成背景主线。
- Design Goal 中是否避免了“让用户”“让页面”“让首页”等 Design Focus 句式。
- 如果输出了 Design Focus，是否每条都包含其他章节没有表达的真实设计取舍；如果没有真实设计难点，是否已省略 Design Focus。
- Wireframe 是否仅在用户明确要求时输出，并符合本节的页面数量、页面布局与主次规则？
- 是否把当前需求事实误写成通用规则；如果是，只保留抽象判断方法，不保留具体业务动作或对象。
- 是否存在上个项目残留内容；如果有，必须替换为当前项目内容或占位。
- 是否完成跨章节压缩，同一事实是否只有一个主归属；重复出现时是否确实增加了新的评审判断。
- 写入完成后是否运行 `scripts/validate_design_definition.py {输出文件}`；校验未通过时不得交付。若出现重复内容 warning，先按内容归属表压缩一次再重新校验；warning 是复查信号，不是固定篇幅上限。
